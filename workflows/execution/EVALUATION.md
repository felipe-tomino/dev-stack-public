# Comparing executor strategies

Read only when an authorized change folds a worker into the principal, changes delegation strategy or removes an outcome-relevant guardrail. This is not a stage of ordinary coding work. The execution method owns permissions, scope and completion.

## Establish a meaningful baseline

Choose one change and a concrete hypothesis: for example, keeping a feature's investigation and implementation in one context reduces integration failures. Save the previous configuration/instructions outside active discovery so the comparison is reversible without leaving competing agents or skills enabled.

Use representative, replayable tasks with independently observable acceptance, not prompts that merely ask the model to recite its routing policy. Start with roughly ten varied tasks and two runs of each variant in fresh sessions; use a smaller targeted set when the change affects a narrower behavior and state that limit. Include every affected worker chain and important safety boundary. Keep the model, effort, tool access, repository snapshot and starting data comparable. Do not compare different models and attribute their difference to delegation.

Useful cases to select from the user's actual executor work:

| Case | Observable acceptance |
| --- | --- |
| Small local correction | The reported behavior is fixed without unrelated files or a mandatory full-suite run. |
| Cohesive API feature | Caller, implementation and failure contract agree in an exercised request. |
| Coupled frontend/backend change | The real interaction uses the agreed contract; no integration gap between workers. |
| Visual adjustment | The surface preserves the design system and configured designer route without an unnecessary handoff. |
| Mid-task user correction | The final result incorporates the correction consistently across affected decisions. |
| Noisy log investigation | A bounded, source-backed cause or explicit unknown returns without flooding the principal with raw logs. |
| Independent research questions | Each answer has primary evidence and the synthesis preserves relevant disagreements. |
| Consequential read-only review | Findings trace to actual boundaries; reviewed files remain unchanged. One reviewer may cover both review axes. |
| Independent implementation slices | Both deliverables satisfy their contracts after integration, not merely in worker reports. |
| Restricted-tool work | The required operation succeeds within the actual permission boundary; prohibited actions remain unavailable or denied. |

## Run and compare

1. Run both variants against isolated, equivalent inputs. Use authorized accounts only; do not replay production writes, copy credentials or enlarge permissions for an evaluation.
2. Check actual task outcomes against acceptance, including failure paths. Record which skill or worker was selected, but do not count correct routing or a convincing final message as task completion.
3. Record correctness, omitted requirements/regressions, time to verified completion, total principal-plus-worker usage/cost when available, and user intervention/integration rework. Report unavailable metrics rather than estimating them. Cached prompt length alone is not a cost measure.
4. Inspect individual tasks that changed from pass to fail as well as aggregate results. Keep the folded strategy when it preserves required outcomes and boundaries with justified coordination benefits; retain or restore the worker when its context separation materially improves results or enforces a necessary capability boundary.

## Keep maintenance proportional

Instruction wording edits need link/discovery checks, not a new benchmark. A runtime prompt-template change needs native rendering/discovery and tool/permission preservation checks; those checks are not productivity evidence. Broader efficiency claims require the task comparison above. Revisit temporary model workarounds when actual evidence or a model change calls them into question, not on a compulsory maintenance schedule. Rarely used authorization or data-integrity protections are not dead weight.

Report the tested variants, model/runtime, tasks/repetitions, observed outcomes and limits in the authorized delivery or existing change record. Remove temporary probes and deactivate the losing variant; do not leave compatibility wrappers, install an evaluation framework or add a permanent specialist team merely to run the comparison.
